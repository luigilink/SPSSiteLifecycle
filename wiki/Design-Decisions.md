# Design decisions

This page records the main decisions behind SPSSiteLifecycle and the facts they rest on. It changes only through a pull request, so that the reasons stay visible.

The measurements come from a Microsoft 365 demonstration tenant of about 10,000 sites. Read them as orders of magnitude, not as guarantees.

| # | Subject | Decision in one line |
|---|---------|----------------------|
| D1 | Name, license, versions | Public, MIT, 0.x pre-releases until a real run is validated |
| D2 | Architecture and settings | One script, one common module, settings in a `.psd1` file |
| D3 | Activity sources | SharePoint, Teams and groups reports (the inactive site policy report later), the most recent date wins |
| D4 | Who decides | A person, in the `Decision` column of the CSV |
| D5 | Unlocked sites | Lock first, direct deletion is off by default |
| D6 | Safeguards of the Act phase | Checks on the whole file, then on each row just before its action |
| D7 | Reading the tenant | Paged, resumable listing, filtered on the server |
| D8 | Input files | Lock-date lists and exclusion lists, in the formats of this tool |
| D9 | Tests and CI | Offline Pester 6 tests, invariant tests, Windows and Linux CI |
| D10 | CSV and Excel | Tolerant reading for the reports, strict structure for the lists and the lock journal, Act reads four columns, separator of the culture |
| D11 | Graph and PnP.PowerShell | Graph v1.0 when the operation is available, PnP.PowerShell otherwise |
| D12 | Scope | SharePoint sites only, never OneDrive |

## D1 - Name, license, versions

- **Name:** SPSSiteLifecycle, in the SPS* family. "Lifecycle" because the tool covers the whole path (report, lock, delete or archive), not only deletion.
- **Visibility and license:** public repository, MIT license, so that as many organizations as possible can use it.
- **Versions:** 0.x pre-releases (tags `v0.*` are published as pre-releases). Version 1.0.0 comes only after a real run, limited to one action (`MaxActions = 1`), has been validated on a production tenant.

## D2 - Architecture and settings

- One entry script, `src/SPSSiteLifecycle.ps1`, with two parameters: `-ConfigFile` and `-Phase` (`Scan` or `Act`).
- One common module, `SPSSiteLifecycle.Common`, with `Public/` and `Private/` functions named `<Verb>-SPSLifecycle<Noun>`.
- **What the script does.** It has no other parameter than these two (a test checks the list), imports the module (a copy that is already loaded from the same folder is used as it is, which is how the tests give it stubbed adapters), and calls the phase. The phases are public functions of the module (`Invoke-SPSLifecycleScan` for the Scan), so that the script stays a few lines and the phase is tested offline. It writes what it did as information, shown by default, and `-InformationAction` is the way to hide it. It exits with `0` when the phase ended and `1` on any error, after one message that starts with `SPSSiteLifecycle stopped:`, says what stopped it and, for the Scan, says that nothing was changed in the tenant. `-Phase Act` answers that the phase is not available in this version, with the same exit code, until the Act issues are done.
- Settings live in a `.psd1` file, read with `Import-PowerShellDataFile` (data only, no code runs): shared keys at the top level, then a `Scan` section and an `Act` section. The aim is a light script and short command lines.
- `Execute` and `MaxActions` are settings of the `Act` section, not parameters. Defaults: `Execute = $false` and `MaxActions = 25`. The typed confirmation, not the setting, is the barrier before any change: the tool shows a banner (file path, date, age of the CSV, number and type of actions), asks for the tenant name, then for `DELETE n`, `ARCHIVE n` or `APPLY n`, and stops when the input is redirected.
- The file is validated as a whole before anything runs. An unknown key stops the tool (a typo must not disable a safeguard), types are strict (`$true` or `$false` only, the string `'false'` is refused), and relative paths resolve against the folder of the file.
- The schema (key, type, default, check) is a data table in the module. The example file and the Configuration page follow it (see D10).
- **A name is read one character at a time.** A tenant name is ASCII: `^[A-Za-z0-9][A-Za-z0-9-]{0,62}$`, matched as it is written, with no case folding and no culture. The first rule, `[a-z]` with `-match`, also accepted the Kelvin sign (U+212A), which `ToLowerInvariant()` turns into a `k`, and a capital I with a dot above (U+0130), which becomes a host that does not exist (#24); none of them could pass the refusal of the Microsoft tenants, but a name that cannot be read is a poor answer. The entries of `RefusedTenants` follow the same rule: an entry that could never be the name of a tenant (an address, a lookalike letter) refuses nothing, so it stops the tool instead of being ignored. The names of the settings are compared the same way (`OrdinalIgnoreCase`, and the setting is kept under the name of the schema): the comparison operators of PowerShell skip a zero-width space and a soft hyphen, so `Refused<zero-width space>Tenants` was read as `RefusedTenants`, kept under its own spelling and never found, and the refusal of the tenants did not apply, with no message. A value of a choice is compared the same way. A message that shows a name writes every character that is not printable ASCII as `\uXXXX` (`ConvertTo-SPSLifecycleVisibleText -AsciiOnly`), so that a lookalike can be told from the letter. The check right before the sign-in (`Assert-SPSLifecycleTenantAllowed`) repeats the rule on the tenant name and requires an ASCII admin address, because a regular expression that ignores the case reads `adm<dotted I>n` as `admin`.

## D3 - Activity sources

- Sources: the SharePoint site usage report, the Teams activity report and the Microsoft 365 groups activity report. All are optional, and at least one is required. The execution report of the inactive site policy is planned as a fourth source, but it is not read yet: its importer waits for a real export that confirms the column names (see the open points).
- The last activity is the most recent date across the sources that were given. The last content modification date of the site (`LastContentModifiedDate`) only adds caution: it is never a proof of inactivity.
- A site that is absent from every report gets a `REVIEW` verdict.
- **Matching.** The SharePoint report is matched by the site ID. The address is a second way in only for a row that has no usable site ID (a report with concealed names). A row that has the ID of another site is never given to a site, even at the same address: that site reused the address of a site that is gone, and it must not inherit the activity of the old one (the rule of the lock dates, D8). A row that rows with different IDs share is not given either, and no row is given to a site whose ID is unknown. In each case the site is in no report, which is `REVIEW-NO-ACTIVITY-ROW`: nothing says that it is inactive. The Teams and the groups reports are matched by the group ID of the site. A report that knows a site and has no date for it counts as a row and gives no date. When dates are equal, the source is the first of SharePoint, Teams, Groups.
- Why: the usage report covers SharePoint only, so a team that is active only in Teams would look inactive. The inactive site policy report covers SharePoint, Teams, Exchange and Viva Engage ([Manage inactive sites using inactive site policies](https://learn.microsoft.com/sharepoint/inactive-site-policy)).
- The CSV keeps `LastActivity`, `LastActivitySource` and one column per source.

## D4 - A person decides

- The Scan CSV has a `Decision` column, filled in by a person: `Delete`, `Archive` or `Lock`. An empty cell leaves the site untouched, and any other value stops the tool before the first action. `SuggestedAction` only helps to filter and to fill in the column: `Lock` for an unlocked site, otherwise `Delete` when the size is at most `DeleteMaxSizeGB` (1 GB by default) and `Archive` above it. There is no separate size threshold for archiving, because the person decides.
- A decision never lifts a safeguard: every check of D6 is repeated live.
- There is no automatic rule in 0.x.

## D5 - Unlocked sites

- By default only a read-only site is deleted or archived: `AcceptedLockStates = @('ReadOnly')`. Adding `'Unlock'` allows the direct deletion of an unlocked site. `NoAccess` is never accepted. Only `Lock` accepts an unlocked site.
- Safe path for an unlocked site: `Lock` (the site becomes read-only and the tool writes the date in a local lock journal with the URL, the site ID and the lock date; nothing is written in the tenant), then `Delete` once `MinLockedDays` (365 by default) have passed.
- **The lock journal** (`LockJournal`, `lock-journal.csv` in `OutputFolder` by default) is the tool's own file, with the columns `Url`, `SiteId` and `LockedOn`. The Act phase adds a row after each successful lock, and both phases read it as a source of lock dates, like the lists of D8. A journal that does not exist yet, or that has no byte, is an empty one, and a site without a lock date is never touched. A journal that exists is read strictly, unlike a list that a person provides, because a row that is ignored or lost could leave an older date of the same site in force. The file must be UTF-8, with a byte order mark or not (a file that holds only ASCII, as French Excel can save it, is UTF-8 too): a file in UTF-16 or in Windows-1252 with an accented letter is refused, and so is a UTF-8 file with a damaged byte, because a byte that is replaced or guessed changes a web address, and the row of a site that has no site ID would no longer match it, so that an older date of the site could win. The file must follow the CSV rules to the letter (D10): a quote inside an unquoted field, a quote that is never closed, text after a closing quote, and a row whose width is not the width of the header (a value too many, a row cut short) stop the tool and name the line of the file. So do a row without a date, with a site ID that is not a GUID, with no site at all or with an address that is not a full web address, a value under a column that has no name, a column that appears twice, a missing column and a column that only looks like `SiteId` (`Site ID`, a hidden character). A new journal is written in UTF-8 with a byte order mark, with the separator of the settings and the date in ISO 8601 in UTC. An existing journal gets the row at its end and nothing else changes: it keeps its separator and its columns (a person may have moved them). The whole file is checked first, with the rules above (reading and adding accept the same files), because adding to a file that breaks them would damage it or lose the row: such a file is refused and left as it is. A journal that Excel opened must be saved as `CSV UTF-8`, because the other CSV formats of Excel are not UTF-8. A program that has the file open, Excel for instance, stops the call with a clear message. The row is written with one call and flushed to the disk, because the date must survive a crash right after the lock.
- Lock dates come from lists given by the user (a URL and a date) or from the journal. The "Action taken on" column of the inactive site policy report will be a third source once its importer exists (see D3). The tenant does not return the date a site was locked.
- Why: a read-only site means that a person already made a decision, and it can be unlocked. In the lab, a read-only site refuses a direct deletion (access denied): the tool unlocks it, deletes it, and locks it back if the deletion fails.

## D6 - Safeguards of the Act phase

Two levels.

**The whole file, before any action** (the tool stops):

- a URL outside the configured tenant;
- a refused tenant: the Microsoft corporate tenants (`microsoft` and `microsoftonline`) are refused by the code and cannot be removed, and the `RefusedTenants` setting only adds names to that list. The settings are checked in both phases, so Scan refuses them too;
- a missing mandatory column (`Url`, `SiteId`, `GeneratedOn`, `Decision`);
- an unknown decision;
- a file older than `MaxCsvAgeDays` (30 by default).

This level is `Import-SPSLifecycleReviewedReport` (#10). It reads the four columns that Act needs (`Url`, `SiteId`, `GeneratedOn`, `Decision`, D10) through the strict reader with a tolerant encoding (D10: the structure is exact, so that no row is swallowed or dropped, and the encoding is the one that Excel writes), and it stops on the first problem, in the order of the file and, for a row, in the order of the list: the address, the site ID, a site that appears twice, the decision, `GeneratedOn`. Every row is checked, with a decision or not, because a file that Excel mangled is not the Scan report, and nothing is checked row after row while the actions run. The decisions that the tool accepts are compared one character at a time (`OrdinalIgnoreCase`): the case and the spaces around do not matter, a hidden character or a letter that looks like another does, and the message writes such a character as `\uXXXX`.

- **The address** is a full web address in the form that SharePoint gives (https, the default port, no user information, a host that DNS reads as it is written) at the host of the tenant, `https://<tenant>.sharepoint.com`. The message of a refused tenant (its site, its OneDrive host and its admin site) is told first; a OneDrive address, the admin site, another tenant and another domain are refused, each with the reason. OneDrive sites are never in the Scan report (D12), so a row that holds one is a mistake, and the tool stops instead of skipping it.
- **A site that appears twice** is found by the canonical form of its address (the case, a trailing slash, the default port and the percent-encoding do not count, see D8) and by its site ID. A row without a decision counts: two rows for one site could carry two decisions, and nothing says which one a person meant.
- **`GeneratedOn`** is read as the dates of the other files are (ISO 8601, the compact form that the Scan writes, and the `CsvDateFormats` setting for a date that Excel rewrote, which the message names). A date in the future stops the tool, with a margin of 5 minutes for the clocks of two machines. A date older than `MaxCsvAgeDays` stops it, and says to run the Scan again. Each row has its own date and each is checked; the date of the file, for the banner and for the age, is the oldest, and each row keeps its own for the check of the content (a site changed since `GeneratedOn`).
- An empty list of decisions is not an error: the tool says that there is nothing to do. The function gives the rows that have a decision with their line in the file (which a person finds in Excel), the count of each action, and the date and the age of the file. It reads the file and nothing else.

**Each row, right before its action** (the row gets a `SKIP-` or `REVIEW-` verdict and the run continues):

- the site still exists, with the same `SiteId` (a URL can be reused);
- its lock state is accepted (D5);
- it is not a channel site, a hub site, the root site, a system site, a home site or a OneDrive site;
- for an archive, its template is one that Microsoft 365 Archive supports (`SKIP-NOT-ARCHIVABLE`). The list is a table in the module, taken from [Manage Microsoft 365 Archive](https://learn.microsoft.com/microsoft-365/archive/archive-manage#site-templates-supported). A template that Microsoft adds later is refused until the table is updated;
- its Microsoft 365 group, if any, is active (a group state that was not read counts as not active);
- its content was not modified since `GeneratedOn`;
- no retention policy or hold is known (best effort: the tool cannot see every Microsoft Purview policy);
- for a deletion, its size is known and not above `DeleteMaxSizeGB` (1 GB by default). A size that is missing, blank, negative or not a number is unknown, never zero.

Always on: report only by default, double typed confirmation, `MaxActions`, a stop after 3 consecutive errors (not configurable), and explicit verdicts. A rule of the code runs through all of them: an input that is missing or cannot be read never leads to an action, it leads to a `SKIP-` or `REVIEW-` verdict, or it stops the tool.

## D7 - Reading the tenant (Scan)

- The activity comes from the reports. The live state (lock state, group, template, size, archive status) comes from a paged listing of the tenant through the SharePoint admin API, about 1,500 sites per page, filtered on the server by lock state when a single state is requested. There is one checkpoint per page, an automatic resume and a progress display. Reports and listing are joined by site ID.
- There is no targeted mode (reading only the sites of a list) in 0.x.
- **The listing** (`Get-SPSLifecycleTenantSite`) is the one call that the Scan makes to read the tenant. Its logic is made of pure functions that the tests cover offline (the record of a site, the server filter, the summary, the checkpoint store and the pager), and the calls to the tenant are in the adapters of D11: the sign-in, the sign-out and the read of one page. The pager asks for a page, saves it in the checkpoint, gives its sites to the pipeline, and only then asks for the next one, so that the memory does not depend on the size of the tenant.
- **The call.** The paged call of the SharePoint admin API (`Tenant.GetSitePropertiesFromSharePointByFilters`: with the details, the OneDrive sites left out by the server, and the token that the page before gave) is used when the installed PnP.PowerShell has the types and the members that it needs. That is checked on the types themselves, on the first call, and `Get-PnPTenantSite -Detailed` is used otherwise, with the reason in the summary: it reads the tenant in one page and cannot be resumed. The end of the listing is a page with no token, not an empty page, because a page that holds no site of the filter comes back empty with a token (7 pages for the 9 read-only sites of the lab). A page that cannot be read is asked again twice, after 5 s and then 10 s, before the listing stops, and the listing also stops on a token that was already asked (it would never end), on a source that gives no page, and on a page that has no token or whose token is not a text (a missing token would read as the end of the listing, and every site after it would be left out of the inventory).
- **One record, whatever the call.** The size is `StorageUsage` (in MB) on the object of the paged call and `StorageUsageCurrent` on the object of the cmdlet; the record of a site has one shape, so that the Scan does not know which call listed the site. A property that the call did not load reads as `$null` in PowerShell (the exception of the getter is swallowed), as an empty one does, and a Scan that took it for "no group" or "not a hub site" would hide a safeguard for every site. Every site is therefore read once for each of its twelve properties, and when one of them reads `$null` that site is read through reflection, which shows the exception: a page with a property that was not loaded stops the listing and names the property and the site, whichever site of the page it is (the review showed that reading the first site only let a later site's date that was not loaded become "no date", and the Scan gave it a delete verdict). A null is never stored as a false, an empty GUID or a missing date. The size is a whole number of megabytes: a blank size is not known (null, and the Scan gives such a site a review verdict, not a size of zero), and a boolean, a fraction, a text, a value out of range or a negative one stops the listing, because a cast would have read them as 0, 1, 2 or nothing. A site ID that is all zeros is refused. A group ID that is all zeros is kept as a text, and the Scan core reads it as no group. The text of an error that names a site is built only when something is thrown: building it for every site took 295 µs a record, and a record now takes 30.
- **The checkpoint** is the `listing-checkpoint` folder of the output folder: a manifest, one file per page (a CSV with every cell quoted, read back with the strict reader, because JSON would turn a title that looks like a date into a date) and a lock file, so that two runs cannot write it together. A page is written to a partial file, hashed (SHA-256), moved into place, and only then listed in the manifest. A run takes the checkpoint up only if its listing did not finish, it is for the same tenant, filter and options (the call that is used, and what is asked about OneDrive and personal sites), it is not older than 24 hours from the start of the listing (the first pages are the oldest), its dates can be true (neither the start nor the last update is more than 5 minutes in the future, and the last update is not before the start: that is what a clock that was set back looks like), its manifest is the one that the tool writes, every page is there with the hash that was saved, and the pages form a chain: each entry keeps the token that its page was asked with and the token that it gave, the first page is the one asked with the empty token, each page is the one that the page before gave the token of, and the last token is the one that the manifest goes on with (without that, an entry removed from the middle of the manifest takes its page out of the inventory although its file is intact). A manifest that says that the listing is running and complete, and lists no page, is refused as well, and so is one that lists no page and has a token to go on with (the first page is asked with none: that token would be asked as it is, and the pages before it would be lost without anything saying so). What the checkpoint holds is compared as it is written: the tokens, the state, the names of the page files, the filter, the options and the hashes are compared with the ordinal comparison, because the comparison operators of PowerShell follow the rules of a culture, which ignore some characters (a soft hyphen is not shown), and a token that differs by one of them would have been asked from the server as it is, and an empty token is tested by its length. Otherwise the run says why and starts again, and `Restart` starts again without any check. A listing that finished is never reused to answer a new Scan: its pages are deleted, and the manifest says that it finished.
- **Why a checkpoint was not taken up.** The reader gives the reason as a sentence for the person who runs the Scan, and that sentence can name the tenant or the filter that the checkpoint was made for. Next to it is a code, one of a few fixed words that name nothing (`damaged`, `other-version`, `finished`, `other-tenant`, `other-filter`, `other-options`, `clock`, `too-old`), which the summary keeps as `StartCode` (`restart` when the listing was asked to start again). A report that is meant to be shared (the lab, D9) tells the reason from the code and never from the sentence.
- **A site that comes twice.** A page that is asked again, or a tenant that changes while it is read, can give a site twice. It is kept once and counted when the two readings agree on the fields that a safeguard or a verdict reads (address, template, lock state, group ID, hub flag, the two Teams flags, archive status, size and date of the last change, compared by a 64-bit digest; not the title, which no verdict reads), and the listing stops and names the site when they do not, because the first reading is not always the true one: a hub flag that went from false to true, a size that went from 100 to 5,000 MB or a last change that went from two years ago to an hour ago would have kept the reading that protects less, and dropped the other without a word. A size or a date that is not known is not zero and is not a date: it differs from every one that is known. After a resume the first reading comes back from the checkpoint, so the same conflict would come back at every run that takes it up: the message says to start the listing again from the first page (`Restart`). A site with no site ID is never taken for another. The pager remembers one 64-bit number per site, which is 61 MB for 260,000 sites where the text of the fields would have taken 201 MB, and the digest costs about 11 µs a site, which is 3 of the 12 seconds that the pager takes for 259,500 sites.
- **The home site** is protected (D6), and nothing in the listing says which site it is, so the listing reads it: right after the sign-in and before the first page, `Get-SPSLifecycleHomeSiteUrl` (an adapter, D11) asks the tenant with `Get-PnPHomeSite` and the address goes into the summary of the listing (`HomeSiteUrl`, empty when the tenant has none). The Scan core takes it through a script block (`HomeSiteUrlSource`) that it calls once, when the first record comes, because the pipeline binds its parameters before the listing signs in. The rule is the one of every safeguard (D6): a home site that is not known would be suggested like any other site, so a read that fails, and an answer that is not the https address of a site, stop the run before any page. An interrupted listing that is taken up reads the home site again, since it may have changed. The call has not run against a tenant yet: the lab script (`tools/lab/Test-TenantListing.ps1`) reports a `home-site` check that says whether the tenant has a home site, and never shows its address.
- **The Scan run** (`Invoke-SPSLifecycleScan`) puts the pieces in order, so that a mistake costs as little as possible: the settings, the activity reports, the lock date lists, the lock journal and the exclusion lists are read first, and a problem in any of them stops the run before the sign-in window opens. The pipeline then starts the report (which creates the output folder, refuses to replace a report of the same second, and checks the settings for the core again) before the listing signs in, because a pipeline runs the `begin` block of each of its commands before the first record. A run that stops half-way leaves no report that looks complete, and an interrupted listing is taken up from its checkpoint the next time. The run gives a summary (the sites read, listed and left out, the verdicts and the suggested actions, how the sites were listed, the time, and the path of the report) and writes it as a few lines of information: the numbers are written the same way whatever the culture of the machine, the verdicts are sorted by count and then by name, and the lines name no site and no title. The Scan never changes anything: the tests give it every adapter that the Scan uses, and a tripwire for each command of PnP.PowerShell that changes a tenant (a call of one fails the test).
- **The Scan core** (`ConvertTo-SPSLifecycleScanRow`) is a pure function: it takes the records of the listing, the settings and the indexes (lock dates, exclusions, activity reports), and gives one row per site with the columns of D10. It reads nothing and changes nothing, so that the whole Scan logic is tested offline and the listing can change without touching it. The rows go down the pipeline one at a time, straight to the report writer, so that a report of 260,000 sites needs no more memory than one of 100, and what was done is counted into a summary object (sites read, listed, left out, and rows per verdict and per suggested action).
- **What the core leaves out, and what stops it.** A OneDrive site is left out and counted (D12), and so is a site whose address is not in the form that SharePoint gives: an https address that parses, whose host is the one that DNS sees (no soft hyphen, full-width letter or bidirectional isolate that the IDNA mapping changes or refuses), with no dot of the DNS root and no port other than the default one. The spellings that can hide the OneDrive host, the root site or an excluded site are too many to list when they are combined, and a SharePoint address never has them; a site left out by mistake is safe. A site is also left out when its lock state is not in `Scan.LockStates`, whether the server filtered the listing or not. A record that has no address, or no usable site ID (empty, not a GUID, all zeros), or a group ID that is neither empty, nor all zeros (a site without a group) nor a GUID, or a hub flag or a channel flag that is not `True` or `False`, or no template, or a content change that is not a date, stops the Scan and names its number and its address. Such a record cannot be matched with the reports and the lock dates, or it would make a safeguard silently not apply (a group ID that reads as "no group" leaves out the Teams activity of the site, and a missing hub flag reads as "not a hub site"), the Act phase could not confirm it, and it can only come from a defect of what reads the tenant, which a plausible verdict would hide. The tenant always gives these values, so this is not a case that a run meets.
- **Measured** (macOS, PowerShell 7.6, made-up sites, the listing streamed, an index of 222,000 lock dates): the core takes 260 to 290 µs per site, 66 to 75 s for 259,000 sites (several runs), and writing the report takes about 700 µs more per site. It took 968 µs per site (250 s) before two changes that the garbage collector asked for (D9): the constant tables of the verdict engine (protected paths and templates, archivable templates) are built once instead of at every call, which created 31 objects per site, and the lock date entries, which stay in memory for the whole Scan, are hashtables. The tests run 5,000 and 20,000 sites and compare the times, so that a time that grows with the square of the size, which Windows makes easy (D9), fails after a minute.
- Measurements (10,030 sites, 9 of them read-only):

| Read | Time |
|------|------|
| `Get-PnPTenantSite -Detailed`, whole tenant | 36 s |
| same cmdlet, server filter on `ReadOnly` | 8.7 s (the same 9 sites as a client-side filter) |
| paged listing | 2.3 to 2.8 s per page of 1,500 sites, resumable |
| one site by URL | 0.92 s one by one, 0.31 s in batches of 100 |

- Measured without a tenant (macOS, PowerShell 7.6, a page source that gives made-up sites): the checkpoint takes 22 µs to write and 32 µs to read a record, and the pager lists 259,500 sites in 173 pages in 12 s (47 µs a site, the page source included), or in 11 s when it resumes at the half (86 pages are read from the checkpoint). The first measures were 10 s and 9 s, before the guard against a site that comes twice read the fields that a verdict uses. The tenant is the slow part: at the 2.3 to 2.8 s per page of the lab, 173 pages would take 7 to 8 minutes, which has not been measured on a tenant of that size.
- Reading a site by its site ID was refused in the lab (access denied). The usage report can have an empty `Site URL` (concealed names, BYOK, Customer Lockbox), and it has neither the lock state nor the group: it cannot replace the listing.

## D8 - Input files

SPSSiteLifecycle is a new tool. It does not read the files of any earlier script: its input formats are its own. All inputs are plain CSV files that follow the rules of D10.

- **Lock date lists** (`LockDateFiles`): a `Url` column, a `LockedOn` column and an optional `SiteId` column. The structure of the file is read strictly, with a tolerant encoding (D10). A header that only looks like `SiteId` (`Site ID`, `Site_Id`, a hidden character) stops the tool, because the site ID of every row would be lost without a message. When a site appears in several lists or in the lock journal (D5), the latest date is kept: a later lock date can only delay a deletion. On equal dates the first source wins (the lists in the order of the setting, then the journal), and its file name goes to the `LockedOnSource` column. A date before 2000-01-01 stops the tool, in a list and in the journal: SharePoint Online did not exist then, and a spreadsheet writes a blank date as `1900-01-01`, `1899-12-30` or `1970-01-01` (and a program as `0001-01-01`), so a site would look as if it had been locked for ever and would pass any `MinLockedDays`. The error is the dangerous one, an earlier date, so it stops the tool instead of being ignored. Adding to the journal refuses such a date too, with the same floor (`Get-SPSLifecycleEarliestLockDate`), so that the tool never writes a journal that it would then refuse to read, and a machine with a wrong clock cannot make the journal unreadable. A date in the future only delays a deletion, and is accepted.
- **Which site a lock date belongs to.** A row that has a site ID is that site, whatever its address: a renamed site keeps its date. A row that has none is matched by the canonical form of its URL. A row whose site ID is another one is ignored, even when the address is the same, because that site reused the address of a site that is gone and must not inherit its date. When the ID of a site is unknown, no date is found: the tool cannot tell whose date a row would be, because a replacement site at the address of a site that was locked years ago would inherit its date and become a candidate for deletion, and a row that is left out could hide the more recent lock of the site itself. A site without a lock date is never touched, which is the answer that is safe in both cases. Within a file, two rows with the same site ID are one site (the latest date), and two site IDs on the same address stay two.
- **Exclusion lists** (`ExclusionFiles`): a `Url` column. A listed site gets `SKIP-EXCLUDED` in Scan, and Act checks the lists again, because a decision never lifts a safeguard (D4). The structure of the file is read strictly, with a tolerant encoding (D10): a row that is swallowed or dropped would protect nothing. Every filled cell must be a full address on one line: a row that cannot be read would protect nothing, so the tool stops instead of skipping it. The lock date lists are more lenient, because a date that is not read only keeps a site safe.
- URLs are compared in a canonical form: the case, the trailing slashes, the default port, a query and the percent-encoding do not count (`%C3%A9quipe` and `équipe` are the same address). The same form is used for the lists, the reports, the root site, the home site and the system paths, so that a safeguard cannot miss a site because of the way its address was written.
- No saved inventory is read. The paged listing keeps its own checkpoint files to resume an interrupted Scan (D7), and the Scan CSV is the reviewed list that Act reads.
- **Paths.** A relative path typed on the command line is relative to the location of the PowerShell session, and a relative path in the settings file is relative to the settings file (D2). The tool never uses the working directory of the process: the .NET file methods (`File.Open`, `Path.GetFullPath`, `Directory.CreateDirectory`) use it, and `Set-Location` does not change it, so a check by `Test-Path` and the file that is then opened could be two different files, and a run could read a same-named file from the folder where PowerShell was started. Every path goes through `Resolve-SPSLifecycleFileSystemPath` before a .NET file method sees it (it also refuses a path of another provider, such as `Env:` or `Variable:`), and a structure test checks it (#19).

## D9 - Tests and CI

- Pester 6, pinned to 6.x, with the syntax that Pester 5 and 6 share.
- **Windows runs what Linux and macOS hide.** On Windows, PowerShell 7.3 and later copies the string arguments of every .NET method call (`$object.Method($text)`, `[Type]::Method($text)`) into a log message that it reports to AMSI (`MemberInvocationLoggingOps`; there is no setting to turn it off, and it is a no-op on Linux and macOS). A method that is given the whole text of a file at every record copies the file at every record. The strict parser first read each record with `Regex.Match($text, $position)`: on a Windows runner, 3,000 records of a 27 MB text took 56 s (the 260,000 would have taken about 80 minutes), and the Windows job of the pull request stalled for 14 minutes before it was cancelled, while Linux and macOS read the same file in 3 s. The parser now walks the matches with `Match.NextMatch()`, which takes no argument (260,000 records in 5 s on Windows), the Size tests start with 20,000 records and stop there when that is slow, and the CI jobs have a timeout. The rule for the code: never give a whole file, or any large string, to a .NET method inside a loop.
- **The garbage collector is part of the cost.** PowerShell allocates about 17 KB for each function call, advanced or not (measured on PowerShell 7.6: 4 to 15 µs and 17 to 19 KB for a function that does nothing), so a Scan that makes 30 calls per site produces 600 KB of garbage per site. While that happens, each collection took about 20 times longer when 260,000 `PSCustomObject` were alive (3.5 ms against 0.17 ms with 260,000 hashtables, dictionaries or arrays, which cost almost nothing), and a function that creates many short-lived `PSCustomObject` made the collections slower and slower (the constant tables of the verdict engine: 31 objects per site). The rules for the code that runs once per site: keep what stays in memory for a long time as hashtables, build constant tables once, and count the function calls of the loop.
- Offline by construction: the module loads without PnP.PowerShell or Microsoft Graph. Only the adapter functions (D11) call them, and a structure test checks it by analyzing the code. Outside the adapters a command is called by its name, or through a variable that holds a script block written in the file, and nothing evaluates text (`Invoke-Expression`, `Invoke-Command`, a script block made from a text, `InvokeScript`, `New-Object`, `Add-Type`), so that a command cannot be built at run time to get round the check (`$c = 'Connect-' + 'PnPOnline'; & $c` passed the first version of the test). The test reads the syntax and does not follow a value from one function to another: a caller that hands a text to a parameter typed as a script block is not seen, so the pager and its progress handler are the places to read in a review. The names that hold a script block are kept for each function, not for the file (a parameter typed [ScriptBlock] in one function says nothing about the same name in another); the names of methods are compared without the case, because PowerShell looks a method up without it (`[scriptblock]::create(...)`), and a static call on a type that is not written in the file (one that a variable holds, or that is made from a text) is refused. 184 fixtures show what the rules must flag and what they must let through. A name that holds a script block is also not trusted when it is written by a foreach, by Set-Variable and its relatives, by a parameter such as -OutVariable, by a reference, by a list or typed assignment, or by a parameter of the same name that a script block of the function declares again without a type, and a variable that is written by a name that is not written in the file keeps every name of the function from being trusted. A command is known by its name without the name of its module (`Microsoft.PowerShell.Utility\Invoke-Expression` is `Invoke-Expression`, and `Microsoft.PowerShell.Utility\Invoke-WebRequest` reaches the tenant like `Invoke-WebRequest`), a variable by its name without its scope (`$script:c`, `$local:c` and `${local:c}` are `c`), and an argument that is bound by a colon (`-Name:c`) is an argument of its parameter. A variable can also be written through the drive of the variables (`Set-Item variable:c`, a text that holds a variable after `variable:`), through `Get-Variable` or through `PSVariable`, and then every name of the function is in doubt (every name of the file, for `PSVariable` and for a scope that is given), and a name that a command can write in any scope (the scope is a parameter of `Set-Variable`) is not trusted anywhere in the file, nor is one that a function writes as `$script:c`; a call through `$script:c` is read in the scope of the file, and one through `$global:c` is never followed. An alias made for a command (`Set-Alias`, `New-Alias`, the drive of the aliases) is refused, because a command that goes by another name is not seen by its name. The files that these tests read are set where the module is loaded, so that a test that is run alone cannot pass for want of a file. The tests simulate the adapters.
- **A test never reaches a tenant.** A command of PnP.PowerShell that a test did not replace is the real one: PowerShell loads a module by itself when a command is not defined, and `Connect-PnPOnline -Interactive` opens a sign-in window. The tests of the adapters therefore replace each command with a function that carries a marker and is defined in the scope of the module (`Invoke-Expression 'function script:Name { ... }'`: `Set-Item Function:\Name` inside `& $module { }` defines the function in a child scope, which is gone at once, and the test then calls the real command), check before each test that the command that would run is that function, keep a function that throws for every command that signs in or reads the tenant, and put it back after each test. The one test that looks at the real types of the installed PnP.PowerShell loads the libraries of types only, in a process of its own that keeps only the modules of PowerShell on its path, and checks that neither the module nor a sign-in command is there. A test run that hangs with no output probably waits for a sign-in.
- **A closure is cut off from its module.** A script block that is made with `GetNewClosure()` no longer sees the private functions of the module that it was written in, and a test double that calls nothing private does not show it. What a script block needs is given as an argument (`PageSourceArgument` of the pager), not captured.
- Invariant tests check every safeguard: report only by default, double confirmation, redirected input stops the tool, `MaxActions`, the stop after 3 errors, the live re-check before each action, protected sites and OneDrive never touched, refused tenant, and an unknown decision or an old CSV stopping the tool before the first action.
- The fixtures are made up (contoso, fictitious GUIDs). The lab cases are a table without identifiers.

Nothing that the module or a library writes as text is passed on, cleaned or not, because a text that has the shape of what is expected can still be a name (the word between quotes after "property" can be the tenant, `contoso#0` has the form of a template, the name of the type of an exception is the name that a person gave it) and no cleaning finds a name that it does not know. What the lab shows comes from lists that are written in the script, in the spelling of the list and never as it was read: the words that SharePoint writes for a lock state and an archive status, the web templates that it has (with their number), the seven sentences that the check of the types of the paged call writes (matched whole), the names of the properties that the tool reads, the lock states of a filter, and the type of an exception when its full name is on a list of the types of the framework, of PowerShell and of the libraries that the tool uses (a namespace says nothing: a library, or a module that is loaded, can have a type named like a site in a namespace that begins like System or Microsoft, and a type that derives from a known one is not the known one). Anything else is shown as not being a name, or as a reason that the script does not know. ## D10 - CSV and Excel

- **Reading is tolerant, except where a lost row is dangerous.** (The activity reports are read tolerantly, as described here; the lock date lists and the exclusion lists follow the structure rules of the next bullet, with the encoding described here.) The separator is detected (comma, semicolon or tab, and a first line `sep=` is skipped). UTF-8 with or without a BOM is read, UTF-16 too, with a fallback to Windows-1252 (the first CSV format that French Excel offers) for a file without a mark that is not UTF-8: that is for the files that a person gives, and the lock journal does not get it (see below). True and false values are read in English and in the words that a spreadsheet writes in another language (`VRAI`, `WAHR`, `VERDADERO`, and so on); any other value stops the tool and names itself. Dates are read in ISO 8601 (`2026-10-28`, `2026-10-28T16:30:00Z`, or the compact `20261028T163000Z`) or in the formats listed in `CsvDateFormats`, for example `dd/MM/yyyy`; the value `Culture` in that list accepts the date patterns of the current culture. The tool never guesses otherwise, because a day and a month swapped in a lock date could silently change whether a site is eligible. An unreadable date stops the tool and names the row, the column and the setting to use. Empty rows added by Excel are ignored, the spaces around the names of the columns are removed (two columns with the same name stop the tool, and a name is compared one character at a time, whatever the case and the culture, because that is how a row finds its properties: a header with a hidden character, a soft hyphen for instance, is not the column that it looks like, and the message shows the character), a duplicate `Url` or `SiteId` stops the tool, and a file still open in Excel gives a clear message. A header that looks like a column that the tool knows, required or optional, without being spelled like it (`Site ID`, `Site_Id`, `Is<soft hyphen> Deleted`) stops the tool too, because a column is read by its exact name and an optional column that seems absent is normal: the site ID of every row, or the deleted flag of a report, would be lost without a message. The message shows the hidden characters as `\uXXXX`. The names are reduced to their letters and digits (decomposed with NFKD, lowercase) to find a lookalike, so an accent or a dot that is a separate character goes away like a hidden character does (`SITEID` and `SI` followed by a combining dot above have the same key; a composing normalization, NFKC, would have turned the pair into a dotted `I`, a letter of its own, and hidden the lookalike), and the message writes a combining mark as `\uXXXX`. A letter of another alphabet that looks like a Latin one is not detected.
- **The lock journal is read strictly.** `ConvertFrom-Csv` is tolerant by design: a quote in the middle of an unquoted field is a letter, a quote that is never closed swallows the rest of the file, and a field beyond the width of the header is dropped, so counting the quotes of a file does not prove that no row is lost (a stray quote and an unclosed quote make an even count). The journal goes through its own parser (RFC 4180 and nothing more): an unquoted field has no quote, a quoted field doubles its quotes, only a separator or a line end may follow a closing quote, a line end is CRLF, LF or CR, and a blank line is a record that spreadsheets add and that is ignored. One regular expression with atomic groups validates a text in a time that is linear in its size (26 MB in 0.12 s, 260,000 records read in 2.4 s on macOS and in 5 s on a Windows runner), and an error names the line of the file, which a person finds in Excel. The encoding is strict as well: only UTF-8 is read (a byte order mark or not), and a byte that is not valid UTF-8 stops the tool, whether it follows a byte order mark, comes in a file without one, or is a whole file in UTF-16 or Windows-1252 with an accent. A decoder that replaces a damaged byte by U+FFFD, or that guesses Windows-1252, turns the address of a row into another address, and the row, which has no site ID, no longer finds its site. The message says to save the file as `CSV UTF-8`, as `Add-SPSLifecycleLockJournalEntry` does.
- **The lists that a person gives follow the same structure rules, with a tolerant encoding (#22).** The lock date lists (`LockDateFiles`) and the exclusion lists (`ExclusionFiles`) were read by the tolerant reader, where a quote that is never closed swallows the rows after it and a value beyond the header or a row cut short is dropped, with no message. Both decide whether a site can be touched: a lost row of an exclusion list protects nothing, and a lost later date of a lock list, while another file holds an older date of the same site, leaves the older date in force. They are now read by `Read-SPSLifecycleStrictCsv` with `-TolerantEncoding`: the structure is exactly the journal's (a text that breaks the CSV rules, a row that is cut short or has a value too many, a value under a column that has no name, a duplicate column, a lookalike of a known column), and every message names the file and the line, which a person finds in Excel. The decision is the one of 29 October 2026: **strict structure, tolerant encoding**, because French Excel saves "CSV (separated by semicolons)" in Windows-1252 and "Unicode text" in UTF-16, and these are the files that a person gives, whereas the journal is written by the tool and stays UTF-8 only. One thing is stricter than the tolerant reading was: **a byte order mark is a declaration**, so after a UTF-8 mark an invalid byte, and after a UTF-16 mark a lone surrogate or a left-over byte, stop the tool (`ConvertFrom-SPSLifecycleCsvByte -StrictAfterMark`) instead of becoming U+FFFD, which would change a web address and leave a site unprotected. Only a file without a mark keeps the guess (UTF-8, then Windows-1252), which is harmless for web addresses, GUIDs and dates, that are ASCII. What stays tolerant is the meaning of a row, not its structure: a lock date row without a date is ignored (it says nothing about its site), the `SiteId` column is optional, the empty rows that Excel adds are ignored, and the activity reports are still read by the tolerant reader, because a report row that is lost gives a site with no activity row, which is `REVIEW-NO-ACTIVITY-ROW`: it fails closed. Measured on macOS with made-up rows, a list of 260,000 rows is read in 17 s for the lock dates (with a site ID) and in 10 s for the exclusions, against 11 s and 6 s before: the time is linear, and a test compares 4,000 and 16,000 rows so that a time that grows with the square fails.
- **Act reads four columns only:** `Url`, `SiteId`, `GeneratedOn` and `Decision`. Everything else is read again from its source or live, so what Excel changes (dates, `VRAI` and `FAUX`, decimal commas) cannot alter an action.
- **Writing:** UTF-8 with a BOM and the separator of the current culture (a semicolon for French) unless `CsvDelimiter` says otherwise. A field that holds the separator, a quote, a line break or a tab, or that starts or ends with a space, is quoted: an unquoted field loses its leading spaces when PowerShell reads it. The lines are written one at a time to a partial file in the same folder, which takes the name of the report only when it is complete, by a move that refuses to replace a file: a run that stops half-way leaves no report that looks complete, and a reviewed report is never replaced. The records go through the pipeline, because PowerShell keeps several KB for each record whose properties it has read (measured: 260,000 sites written from the pipeline peak at 204 MB; the first version, which built the report in memory from an array, used about 22 KB per site, which is about 5.6 GB for 260,000 sites by extrapolation). A character that UTF-8 cannot hold (half of a surrogate pair) is written as U+FFFD, because one odd title must not stop a report of 260,000 sites. Sizes are whole megabytes (`StorageUsedMB`, rounded half away from zero, with every digit of an integer or a decimal kept until then) and dates are ISO. `GeneratedOn` is written in the compact form `20261028T163000Z` (UTC), which is meant to survive a round trip through a spreadsheet unchanged. `Title` is neutralized against formula injection ([CWE-1236](https://cwe.mitre.org/data/definitions/1236.html)) and is never read by Act. There are no owners, because they are personal data.
- **Columns:** `Url`, `Verdict`, `SuggestedAction` and `Decision` first, then `SiteId`, `Title`, `Template`, `GroupId`, `IsTeamsConnected`, `LockState`, `ArchiveStatus`, `StorageUsedMB`, `LastActivity`, `LastActivitySource`, `InactiveDays`, `SharePointActivity`, `TeamsActivity`, `GroupActivity`, `ContentModified`, `LockedOn`, `LockedOnSource` and `GeneratedOn`.
- **Documentation** is written in English with Microsoft Learn references only. The Configuration and Verdicts pages are generated from the settings schema and the verdict table. A test fails when a generated page differs from the committed file, so a key without documentation turns CI red.

## D11 - Graph and PnP.PowerShell

- Microsoft Graph v1.0 is used when the operation exists there as a generally available API. PnP.PowerShell (the SharePoint admin API) is used otherwise. Beta APIs are not used in production.
- Each operation has one private adapter function (usage report, site state, lock, site deletion, archive, group state, group deletion), and the adapters are the files of `Private/Adapters`. Those of the Scan are the check of the PnP.PowerShell version (3.0 or later), the sign-in (interactive, with the `ClientId` of the settings; the connection is kept in the session and is not made the current one of the PowerShell session), the sign-out, the read of one page of sites, and the request of the paged call, which is the one place where the property names of the admin API are written. Every call of an adapter that reaches the tenant carries `-ErrorAction Stop`: a command of PnP.PowerShell that writes an error and goes on is not an exception, so a cmdlet that gave some sites and then wrote an error became a last page that looked complete (the pager retries only what throws), a query that wrote an error left a collection that was not loaded, and a sign-in that wrote an error and gave nothing left a session with no connection, whose later calls would have used the connection that the PowerShell session already holds, which may be the one of another tenant. A sign-in that gives no connection stops the tool. A structure test fails when a call of an adapter that reaches the tenant has no `-ErrorAction Stop` (read from the syntax, splatted calls included), and when a command that signs in or reads the tenant (`Connect-*`, `*-PnP*`, `*-Mg*`, `Invoke-RestMethod`, `Invoke-WebRequest`), or a type of the admin API, of CSOM or of PnP.PowerShell (`Microsoft.Online.SharePoint`, `Microsoft.SharePoint.Client`, `PnP.PowerShell`, `PnP.Framework`), is named anywhere else, in a command, a type expression or a string. When Graph covers an operation, only its adapter changes, and the tests do not.
- Coverage on 28 October 2026, from the Microsoft Graph metadata and Microsoft Learn:

| Operation | Graph v1.0 | Graph beta |
|-----------|------------|------------|
| Usage reports, group state, deleting the group of a group-connected site | yes | yes |
| List sites with lock state, template and size | no ([`getAllSites`](https://learn.microsoft.com/graph/api/site-getallsites?view=graph-rest-1.0) is application-only and has none of these) | the lock state and template properties exist |

## D12 - Scope

SharePoint sites only. OneDrive sites are never listed for action and never touched, and there is no option to include them. Scan leaves them out and counts them in its summary. Act refuses any OneDrive row (`SKIP-ONEDRIVE`). A site whose address is not in the form that SharePoint gives is treated the same way, because nothing can say that it is not a OneDrive site.
